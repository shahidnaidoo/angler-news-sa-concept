# Shared standards for simple business websites

These rules are the same across client brochure sites. Use the installed `$clio` skill for its workflow and linked QA/ZDD checklists; if that skill is unavailable, locate the project’s supplied CLIO package before proceeding. Keep business identity, source material, requested sections, and visual direction in the project brief.

- Default to a one-to-four-page static marketing site, honoring the requested scope. Default to no backend, accounts, database, or CMS. For public-page changes in an existing application, preserve its stack, backend and data contracts. Use verified call/email links; add a real submission service only when requested and fully configured.
- Before calling the website done, complete the workflow QA checklist for the actual artifact and agreed local-preview or release milestone. Record each required skill/template by exact source and version, its applicable checks, status and evidence. Required failures or unverified items block a completion claim; recheck affected evidence after fixes. Both Zero Defect Delivery (ZDD) and Tech Local Standards are mandatory completion checklists, alongside TDD. Read the workflow's source-mapped ZDD checklist and preserved source PDF; record applicability and unresolved source wording honestly. This does not add an approval round.
- Follow the installed Tech Local standards and the project's `.techlocal/standards.yml`. Add the manifest for a new Tech Local/client repository and run the bundled audit before handoff. Do not duplicate the full policy here.
- Use test-driven development for changed behavior: first demonstrate the failure, implement the behavior, then run the regression check. Test applicable journeys such as navigation, contact destinations, routes, and requested gallery controls. A simple visible navigation need not become a collapsible menu to match inherited tests.
- Use semantic HTML, consistent design tokens, responsive images, accessible focus and keyboard behavior, and a deliberate mobile composition. Marketing sites may use shadcn when useful; it is not mandatory.
- Work from real references and assets into the working site. Generated website mockups are opted out for this workflow. Keep business-specific creative choices in the brief.
- Verify each UI change visually in the Codex in-app browser at desktop and mobile sizes. Exercise buttons and navigation; fix defects until the changed behavior and appearance are correct. Commit/push operations alone do not require a visual check.
- Use Chrome for authenticated GitHub, deployment, and other service-provider access. Follow the current tool documentation.
- Use subagents for bounded independent tasks, inheriting the parent's model and reasoning level. Never downgrade without explicit user permission.
- Verify factual claims, testimonials, project details, and contact information against supplied or public sources. Visibly identify user-requested fictional business samples and exclude them from release output. Explicitly permitted placeholder contacts stay noninteractive in a local preview; never link dummy phone/email values.
- Licensed stock may illustrate the subject when business photos are unavailable; record its source/license and do not imply it depicts the client's completed work. Legitimate illustrative assets may remain in release output.
- Make reasonable choices with minimal user input. Ask only for consequential missing information. Do only the requested work and changes that directly support it.
- Keep provider credentials out of source and client bundles. A submitting contact form must satisfy the applicable Tech Local server-side anti-abuse policy.
- Run applicable production build, lint, type, formatting, behavioral, accessibility, and local standards checks. Record evidence accurately; do not claim physical-device, browser, or field-performance checks that were not performed.
- Preserve existing user work and servers. Never stop a server you did not start. Do not publish or replace a live site without authorization.
- Keep learning notes local to the project. Do not automatically modify a shared or globally installed skill after each website; workflow maintenance requires authorization.
